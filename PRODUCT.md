# Product

## Register

product

## Users

Atomic Tools is a collection of lightweight, single-purpose web utilities. The primary user is Jason, with occasional public sharing when a tool naturally supports it. Each tool should respect its context of use: quick lookup for Wordle Checker, playful creation and sharing for Madlib Maker, focused clipboard conversion for Rich Text Markdown, and dense comparison work for AI Coding Subscriptions. The root index is a launcher, not a marketing site.

## Product Purpose

Atomic Tools exists as a private bench of sharp utilities: fast to open, easy to understand, and narrow enough that each tool can solve its job without setup friction. Success means the first screen gives the user the real tool, not a wrapper page, and the interface makes the current state, available actions, and output path obvious.

## Brand Personality

Direct, practical, and intentionally crafted. Atomic Tools should feel purposeful and low-friction without becoming plain or careless. Individual tools may vary in personality when the job calls for it: analytical for comparison tables, game-faithful for Wordle, expressive for Madlib Maker, and quiet for conversion workflows.

## Anti-references

Avoid landing-page polish, sales copy, ornamental introductions, decorative gradients, generic SaaS card stacks, and design flourishes that slow down the actual task. Do not force one universal theme across tools when the domain calls for a different treatment. Do not hide useful state behind vague copy, novelty interactions, or visually clever but low-information layouts.

## Design Principles

- Each tool should do one thing well on the first screen.
- Match density to the job: comparison tools can be dense, writing tools need room, and quick checkers should minimize steps.
- Keep navigation consistent across tools with a clear return path to the Atomic Tools index.
- Make state visible and inspectable: copied, saved, shortened, filtered, unavailable, inferred, or stale states should be explicit.
- Preserve tool-specific character while sharing basic quality standards for spacing, responsive behavior, keyboard flow, contrast, and readable type.
- Use spacing, contrast, type hierarchy, data state, and domain-relevant interaction for emphasis before decoration.

## Tool Identity Model

Atomic Tools should work as a consistent product shell with distinct tool-level experiences. Shared shell elements should remain consistent: the root index, return navigation, baseline accessibility, responsive behavior, focus states, and core interaction quality. Individual tools may vary in palette, density, typography, layout rhythm, and mood when that difference makes the task clearer or more pleasant. Do not homogenize every tool into one visual theme; use the parent product to set quality standards and the specific tool context to drive aesthetic choices.

When using Impeccable, run top-level commands for shared system work such as the index, navigation, audit, accessibility, and documentation. Run per-tool commands for tool-specific shaping, critique, polish, copy, layout, color, and interaction choices.

## Accessibility & Inclusion

Use WCAG AA as the baseline. Interfaces should be keyboard-friendly, screen-reader-legible, reduced-motion-safe, and understandable without relying on color alone. Interactive states need visible focus, clear labels, explicit errors, and responsive layouts that keep controls usable on phone and desktop viewports.
